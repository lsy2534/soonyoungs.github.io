**RAG, CAG, KAG는 모두 LLM이 외부 지식을 더 잘 활용하도록 돕지만, 정보를 가져오고 활용하는 방식은 서로 다르다.**
{: .message }

## 1. 왜 RAG, CAG, KAG를 구분해야 할까?

LLM은 학습 과정에서 습득한 지식을 바탕으로 답변한다. 하지만 기업에서 사용하는 사내 규정, 업무 매뉴얼, 재무 데이터처럼 외부에 있거나 자주 변경되는 정보까지 모델이 항상 알고 있는 것은 아니다.

이 문제를 해결하기 위해 LLM에 외부 지식을 연결하는 다양한 접근 방식이 등장했다.

대표적으로 다음 세 가지를 살펴보자.

| 기술 | 풀네임 | 핵심 접근 |
|---|---|---|
| RAG | Retrieval-Augmented Generation | 질문에 맞는 정보를 검색해서 전달 |
| CAG | Context-Augmented Generation | 질문·사용자·세션·업무 상태 등 상황 맥락을 결합 |
| KAG | Knowledge Augmented Generation | 지식과 관계를 구조화해 검색·추론 |

먼저 기억할 점은 세 기술이 완전히 대체 관계에 있는 것은 아니라는 것이다. 해결하려는 문제와 데이터 특성에 따라 각각 선택하거나 조합할 수 있다. 또한 CAG라는 약어는 문헌과 업계에서 Cache-Augmented Generation을 뜻하는 경우도 있어, 이 글에서는 Context-Augmented Generation이라는 의미로 사용한다.

## 2. RAG (Retrieval-Augmented Generation)

### 검색 증강 생성

RAG는 사용자의 질문이 들어오면 외부 지식 저장소에서 관련 정보를 검색하고, 검색 결과를 LLM에 전달해 답변을 생성하는 방식이다.

예를 들어 사내 취업규칙 문서를 기반으로 AI 서비스를 만든다고 가정해 보자.

사용자가 다음과 같이 질문한다.

> 연차를 반차로 변경할 수 있나요?

RAG 시스템은 질문과 관련된 취업규칙 문단을 검색한 다음, 해당 내용을 근거로 답변을 생성한다.

### RAG 동작 구조

```text
       사용자 질문
            |
            v
     질문 전처리 / Embedding
            |
            v
       Retriever
            |
            v
   Vector DB / 검색 인덱스
            |
            v
     관련 문서 Chunk
            |
            v
      Prompt 구성
            |
            v
           LLM
            |
            v
        답변 생성
```

### 주요 구성 요소

| 구성 요소 | 역할 |
|---|---|
| Document Parser | PDF, DOCX 등의 문서 내용 추출 |
| Chunking | 문서를 검색하기 적절한 단위로 분할 |
| Embedding | 텍스트를 벡터로 변환 |
| Vector DB | 임베딩 벡터와 문서 메타데이터 저장 |
| Retriever | 질문과 관련된 문서 검색 |
| Reranker | 검색 결과의 관련성을 다시 평가 |
| LLM | 검색된 근거를 바탕으로 답변 생성 |

실제 서비스에서는 Vector Search만 사용하는 것이 아니라 BM25와 같은 키워드 검색을 결합하는 Hybrid Search, 검색 결과를 재정렬하는 Reranker 등을 함께 사용할 수 있다.

### 언제 사용할까?

- 사내 취업규칙 및 인사 규정 질의응답
- 고객센터 FAQ 자동 응답
- 기술 문서 및 API 명세 검색
- 사내 업무 매뉴얼 검색
- 자주 변경되는 정책과 지침 검색

### 장점과 한계

**장점**
- 문서가 추가되거나 변경되면 인덱스를 갱신해 지식을 업데이트할 수 있다.
- 검색한 문서와 출처를 답변에 연결할 수 있다.
- 전체 문서를 매번 LLM에 전달하지 않아도 된다.

**한계**
- 검색 결과가 부정확하면 답변 품질도 떨어질 수 있다.
- Chunking, Embedding, 검색 방식에 따라 품질 차이가 발생한다.
- 여러 문서에 흩어진 수치·시간·규칙의 관계를 추론하는 데에는 추가 설계가 필요하다.

RAG의 핵심은 **질문이 들어온 시점에 필요한 근거를 찾아 LLM에 제공하는 것**이다.

## 3. CAG (Context-Augmented Generation)

### 컨텍스트 증강 생성

CAG는 사용자의 질문에 단순히 문서 검색 결과만 붙이는 것이 아니라, 답변에 필요한 **상황 맥락(Context)을 함께 구성해 LLM에 제공하는 접근 방식**이다.

여기서 컨텍스트는 문서 내용만을 의미하지 않는다. 사용자 정보, 권한, 대화 이력, 현재 수행 중인 업무, 업무 단계, 시스템 상태, 시간 정보, 정책 및 제약 조건 등 답변을 상황에 맞게 만드는 다양한 정보를 포함할 수 있다.

예를 들어 사내 HR AI에게 다음과 같은 질문을 한다고 가정해 보자.

> 내 연차가 며칠 남았고, 오늘 반차를 사용할 수 있을까?

단순 RAG는 취업규칙에서 연차·반차 관련 문서를 검색할 수 있다. 하지만 실제로 답변하려면 질문한 직원의 남은 연차, 소속과 권한, 현재 날짜, 휴가 신청 상태 같은 런타임 정보도 필요하다.

CAG 관점에서는 이런 맥락을 모아 정리한 뒤 LLM에 전달한다.

### CAG에 포함될 수 있는 컨텍스트

| 컨텍스트 | 예시 | 활용 목적 |
|---|---|---|
| 사용자 맥락 | 내부 사용자 ID, 부서, 직급, 권한 | 사용자별 응답 및 접근 제어 |
| 대화 맥락 | 이전 질문, 사용자가 이미 제공한 조건 | 대화의 연속성 유지 |
| 업무 맥락 | 현재 업무, 진행 단계, 요청 상태 | 현재 작업에 맞는 답변 |
| 시스템 맥락 | 현재 날짜, 서비스 상태, 처리 결과 | 시점과 시스템 상태 반영 |
| 도메인 맥락 | 회사 규정, 업무 정책, 제약 조건 | 기업 환경에 맞는 답변 |
| 검색 맥락 | RAG가 찾아온 문서와 출처 | 외부 지식에 근거한 답변 |

### CAG 동작 구조

```text
           사용자 질문
                |
                v
       Context Manager
                |
       +--------+---------+
       |        |         |
       v        v         v
    사용자   대화 이력   업무/시스템
    정보                 상태
       |        |         |
       +--------+---------+
                |
                v
       필요한 정책 / 검색 결과
                |
                v
       Context 구성 및 정규화
                |
                v
        Prompt / Input 구성
                |
                v
               LLM
                |
                v
        상황에 맞는 답변
```

핵심 구성 요소는 컨텍스트를 수집하고 정리하는 Context Manager다. 실제 구현에서는 애플리케이션이 인증 정보, 세션 상태, 업무 데이터, 검색 결과 등을 모아 LLM 입력에 반영할 수 있다.

### 언제 사용할까?

- 사용자 권한과 소속에 따라 답변이 달라지는 사내 AI
- 이전 대화와 현재 작업 상태를 이어서 처리하는 AI Agent
- HR 시스템에서 개인별 휴가·근태 정보를 반영하는 서비스
- 고객 등급, 계약 상태, 주문 이력을 고려하는 고객 상담
- 승인 단계나 업무 진행 상태를 이해해야 하는 Workflow Assistant

### 장점과 한계

**장점**
- 같은 질문이라도 사용자와 업무 상황에 맞는 답변을 제공할 수 있다.
- 대화 이력과 Workflow 상태를 활용해 작업의 연속성을 유지할 수 있다.
- 기존 RAG에 사용자·업무 맥락을 추가하는 방식으로 점진적으로 확장할 수 있다.

**한계**
- 어떤 정보를 컨텍스트로 수집할지 설계해야 한다.
- 오래되거나 서로 충돌하는 컨텍스트가 들어가면 답변 품질이 떨어질 수 있다.
- 사용자 권한과 개인정보를 고려해 컨텍스트 접근을 통제해야 한다.
- 컨텍스트가 너무 길어지면 토큰 비용과 지연 시간이 증가할 수 있다.

CAG의 핵심은 **무엇을 검색했는가뿐 아니라, 누가 어떤 상황에서 무엇을 하고 있는지를 함께 고려하도록 LLM 입력을 구성하는 것**이다.

CAG는 하나의 고정된 알고리즘이나 표준 구현을 가리키는 용어라기보다, 문맥을 확장해 생성 품질을 높이는 아키텍처 패턴으로 사용되는 경우가 많다. 따라서 프로젝트에서는 어떤 컨텍스트를 수집하고, 어떻게 검증·갱신하며, 어떤 순서로 LLM에 전달하는지 명확히 정의하는 것이 중요하다.

> 용어 주의: 2024년 논문 *Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks*에서는 CAG를 **Cache-Augmented Generation**이라는 별도의 의미로 사용한다. 이 논문은 제한된 문서 집합을 모델 컨텍스트에 미리 적재하고 KV Cache를 재사용하는 방식을 다룬다. 이 글의 Context-Augmented Generation과는 구분해야 한다.

## 4. KAG (Knowledge Augmented Generation)

### 지식 증강 생성

KAG는 문서의 문장 유사도만으로 답을 찾기 어려운 문제를 해결하기 위해 지식 그래프(Knowledge Graph), 벡터 검색, 논리적 추론 등을 결합하는 접근 방식이다.

RAG가 질문과 유사한 문서를 찾는 데 초점을 둔다면, KAG는 데이터에 포함된 개체와 개체 사이의 관계, 규칙, 수치, 시간 정보를 함께 활용하는 데 초점을 둔다.

예를 들어 다음과 같은 정보가 있다고 가정하자.

- A 직원은 2024년 1월 1일 입사했다.
- B 직원은 2025년 3월 1일 입사했다.
- 회사의 승진 규정은 근속 2년 이상이다.

질문은 다음과 같다.

> A 직원과 B 직원 중 누가 승진 요건을 먼저 충족하나요?

단순히 관련 문장을 검색하는 것만으로는 부족하다. 직원, 입사일, 근속 기간, 승진 규정 사이의 관계를 연결하고 날짜를 비교해야 한다.

### Knowledge Graph란?

Knowledge Graph는 정보를 개체(Entity)와 관계(Relationship)로 표현한 그래프 구조다.

예를 들어 다음과 같이 표현할 수 있다.

```text
[직원 A]
   |
   | 입사일
   v
[2024-01-01]

[직원 B]
   |
   | 입사일
   v
[2025-03-01]

[승진 규정]
   |
   | 요구 근속 기간
   v
[2년 이상]
```

실제 지식 그래프에서는 개체와 관계를 노드(Node)와 엣지(Edge)로 표현하고, 이를 통해 여러 단계의 관계를 탐색할 수 있다.

### KAG 동작 구조

```text
       기업 문서 / 업무 데이터
                |
                v
       Entity 및 관계 추출
                |
                v
        Knowledge Graph
                |
                v
       질문 분석 및 질의 계획
                |
                v
       그래프 + 문서 Hybrid 검색
                |
                v
       논리적 추론 및 계산
                |
                v
               LLM
                |
                v
             답변 생성
```

여기서 중요한 점은 KAG가 Knowledge Graph만 사용하는 단순한 구조가 아니라는 것이다. 대표적인 KAG 프레임워크는 지식 그래프와 원본 문서 Chunk를 연결하고, 벡터 검색 및 논리적 추론을 함께 활용한다.

### 언제 사용할까?

- 인사정보와 조직 간 관계 분석
- 금융 데이터의 수치 및 시간 조건 분석
- 기업 업무 규칙과 프로세스 분석
- 여러 문서에 흩어진 정보 간 관계 추론
- 다단계 질문(Multi-hop Question Answering)

### 장점과 한계

**장점**
- 문서와 데이터 사이의 관계를 명시적으로 표현할 수 있다.
- 여러 단계의 관계를 따라가는 질문에 유리하다.
- 수치, 시간, 업무 규칙 등의 논리적 조건을 활용할 수 있다.

**한계**
- Knowledge Graph를 구축하고 유지해야 한다.
- 개체 추출과 동일 개체 연결(Entity Linking)의 품질이 중요하다.
- 데이터 모델과 관계 스키마를 설계해야 하므로 구현 난도가 높다.

KAG의 핵심은 **정보 자체뿐 아니라 정보 사이의 관계와 규칙을 활용해 답을 도출하는 것**이다.

## 5. RAG vs CAG vs KAG 비교

| 비교 항목 | RAG | CAG | KAG |
|---|---|---|---|
| 핵심 접근 | 관련 지식 검색 | 상황 맥락 구성 | 지식 관계 및 추론 |
| 정보 활용 | 질문에 맞는 외부 근거 검색 | 사용자·대화·업무·시스템 맥락 결합 | 그래프·문서·규칙 활용 |
| 주요 구성 | Retriever, Vector DB, LLM | Context Manager, Session/State, Prompt Builder | Knowledge Graph, Hybrid Retrieval, Reasoning |
| 지식 업데이트 | 검색 인덱스 갱신 | 사용자·세션·업무 상태를 최신 상태로 동기화 | 그래프 및 원본 지식 갱신 |
| 강점 | 다양한 문서에서 필요한 근거 검색 | 상황에 맞는 응답 및 작업 연속성 | 복잡한 관계 및 다단계 추론 |
| 주요 부담 | 검색 품질 관리 | 컨텍스트 수집·정합성·권한 관리 | 그래프 구축 및 관리 |
| 적합한 환경 | 외부 문서 검색이 필요한 환경 | 사용자·세션·업무 상황에 따라 응답이 달라지는 환경 | 관계와 규칙이 중요한 전문 영역 |

세 기술은 다음 질문으로 구분하면 이해하기 쉽다.

- RAG: 필요한 정보를 어디서 찾아올까?
- CAG: 이 질문에 답하려면 사용자와 업무의 어떤 상황 맥락이 필요할까?
- KAG: 정보 사이의 관계를 어떻게 이해하고 추론할까?

## 6. 실제 기업용 AI 시스템에서는 어떻게 선택할까?

기술을 선택할 때는 유행보다 데이터의 특성과 질문의 유형을 먼저 살펴봐야 한다.

### 상황별 선택

| 업무 상황 | 추천 접근 | 이유 |
|---|---|---|
| 사내 취업규칙 검색 | RAG | 문서 검색과 근거 제시가 중요 |
| 자주 변경되는 업무 매뉴얼 | RAG | 문서 갱신 및 검색이 필요 |
| 고정된 제품 매뉴얼 Q&A | CAG 검토 | 제한된 문맥을 반복 활용 |
| 직원별 근속 및 승진 요건 분석 | KAG 검토 | 개체 관계와 날짜 조건 추론 |
| 부서·조직·업무 권한 분석 | KAG 검토 | 여러 개체 간 관계 연결 |

### 서로 조합할 수도 있을까?

가능하다. 실제 시스템에서는 각각의 장점을 결합할 수 있다.

**RAG + KAG**

- 벡터 검색으로 관련 문서 Chunk를 찾는다.
- Knowledge Graph로 관련 개체와 관계를 탐색한다.
- 두 검색 결과를 결합해 답변을 생성한다.

**RAG + CAG**

- RAG로 변경되는 업무 문서와 근거를 검색한다.
- CAG 방식으로 사용자 권한, 대화 이력, 현재 업무 상태를 구성한다.
- 검색 결과와 상황 맥락을 함께 LLM에 전달한다.

**KAG + LangGraph**

- 질문 유형에 따라 검색 또는 그래프 추론 경로를 선택한다.
- 필요한 경우 여러 단계의 검색과 검증을 수행한다.
- 최종 결과를 구조화해 반환한다.

다만 조합이 많아질수록 데이터 동기화, 캐시 무효화, 검색 결과 통합 등의 설계가 복잡해진다는 점도 고려해야 한다.

## 7. 실제 프로젝트에 적용한다면?

HR 문서와 재무 문서를 활용하는 기업용 AI를 개발한다고 가정해 보자.

처음부터 모든 기술을 도입하기보다는 단계별로 확장하는 것이 좋다.

### Step 1. RAG 구축

- PDF, DOCX 문서 파싱
- 문서 구조를 고려한 Chunking
- Embedding 및 Vector DB 저장
- 검색 결과와 근거를 활용한 답변 생성

### Step 2. Advanced RAG

- BM25 + Vector Search Hybrid Retrieval
- Reranker 적용
- 검색 결과 평가
- 검색 실패 시 Query Rewrite 및 재검색

### Step 3. LangGraph 적용

- 질문 유형 분류
- HR / Finance 검색 경로 분리
- 검색 결과 검증
- 실패한 단계만 재시도

### Step 4. KAG 확장

- 직원, 부서, 규정, 계정과목 등의 Entity 추출
- 개체 간 관계 정의
- Knowledge Graph 구축
- 여러 문서에 걸친 관계 추론

### Step 5. CAG 적용

- 사용자·세션·업무 상태 등 필요한 컨텍스트 정의
- Context Manager 구현 및 입력 데이터 정규화
- 사용자 권한과 데이터 최신성 검증
- RAG 검색 결과와 런타임 컨텍스트를 결합해 답변 생성

이 순서가 반드시 정답은 아니지만, 문서 기반 AI를 처음 구축하는 프로젝트에서는 RAG를 먼저 구현하고 실제 한계를 확인한 뒤 확장하는 접근이 현실적이다.

## 8. 마무리

RAG, CAG, KAG는 모두 LLM이 외부 지식을 활용하도록 돕는 기술이지만, 각각 해결하려는 문제가 다르다.

- **RAG:** 필요한 정보를 검색해서 답변한다.
- **CAG:** 사용자·대화·업무 상황 등 필요한 컨텍스트를 구성해 답변에 반영한다.
- **KAG:** 지식 간 관계와 논리를 활용해 추론한다.

중요한 것은 어떤 기술이 가장 뛰어난가가 아니다.

내가 구축하려는 AI 시스템에서 데이터가 얼마나 자주 변경되는지, 문서 규모는 어느 정도인지, 단순 검색으로 충분한지, 여러 정보 간 관계를 추론해야 하는지를 먼저 판단해야 한다.

개인적으로 기업용 문서 AI를 처음 개발한다면 RAG로 문서 검색을 구현하고, 사용자·세션·업무 상태를 반영하기 위해 CAG 패턴을 더한 뒤, 관계 추론이 필요한 영역에 KAG를 적용하는 순서를 추천한다.
