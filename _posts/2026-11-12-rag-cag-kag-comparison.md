**RAG, CAG, KAG는 모두 LLM이 외부 지식을 더 잘 활용하도록 돕지만, 정보를 가져오고 활용하는 방식은 서로 다르다.**
{: .message }

## 1. 왜 RAG, CAG, KAG를 구분해야 할까?

LLM은 학습 과정에서 습득한 지식을 바탕으로 답변한다. 하지만 기업에서 사용하는 사내 규정, 업무 매뉴얼, 재무 데이터처럼 외부에 있거나 자주 변경되는 정보까지 모델이 항상 알고 있는 것은 아니다.

이 문제를 해결하기 위해 LLM에 외부 지식을 연결하는 다양한 접근 방식이 등장했다.

대표적으로 다음 세 가지를 살펴보자.

| 기술 | 풀네임 | 핵심 접근 |
|---|---|---|
| RAG | Retrieval-Augmented Generation | 질문에 맞는 정보를 검색해서 전달 |
| CAG | Cache-Augmented Generation | 필요한 정보를 미리 적재하고 캐시 재사용 |
| KAG | Knowledge Augmented Generation | 지식과 관계를 구조화해 검색·추론 |

먼저 기억할 점은 세 기술이 완전히 대체 관계에 있는 것은 아니라는 것이다. 해결하려는 문제와 데이터 특성에 따라 각각 선택하거나 조합할 수 있다.

## 2. RAG (Retrieval-Augmented Generation)

### 검색 증강 생성

RAG는 사용자의 질문이 들어오면 외부 지식 저장소에서 관련 정보를 검색하고, 검색 결과를 LLM에 전달해 답변을 생성하는 방식이다.

예를 들어 사내 취업규칙 문서를 기반으로 AI 서비스를 만든다고 가정해 보자.

사용자가 다음과 같이 질문한다.

> 연차를 반차로 변경할 수 있나요?

RAG 시스템은 질문과 관련된 취업규칙 문단을 검색한 다음, 해당 내용을 근거로 답변을 생성한다.

### RAG 동작 구조

```text
       사용자 질문
            |
            v
     질문 전처리 / Embedding
            |
            v
       Retriever
            |
            v
   Vector DB / 검색 인덱스
            |
            v
     관련 문서 Chunk
            |
            v
      Prompt 구성
            |
            v
           LLM
            |
            v
        답변 생성
```

### 주요 구성 요소

| 구성 요소 | 역할 |
|---|---|
| Document Parser | PDF, DOCX 등의 문서 내용 추출 |
| Chunking | 문서를 검색하기 적절한 단위로 분할 |
| Embedding | 텍스트를 벡터로 변환 |
| Vector DB | 임베딩 벡터와 문서 메타데이터 저장 |
| Retriever | 질문과 관련된 문서 검색 |
| Reranker | 검색 결과의 관련성을 다시 평가 |
| LLM | 검색된 근거를 바탕으로 답변 생성 |

실제 서비스에서는 Vector Search만 사용하는 것이 아니라 BM25와 같은 키워드 검색을 결합하는 Hybrid Search, 검색 결과를 재정렬하는 Reranker 등을 함께 사용할 수 있다.

### 언제 사용할까?

- 사내 취업규칙 및 인사 규정 질의응답
- 고객센터 FAQ 자동 응답
- 기술 문서 및 API 명세 검색
- 사내 업무 매뉴얼 검색
- 자주 변경되는 정책과 지침 검색

### 장점과 한계

**장점**
- 문서가 추가되거나 변경되면 인덱스를 갱신해 지식을 업데이트할 수 있다.
- 검색한 문서와 출처를 답변에 연결할 수 있다.
- 전체 문서를 매번 LLM에 전달하지 않아도 된다.

**한계**
- 검색 결과가 부정확하면 답변 품질도 떨어질 수 있다.
- Chunking, Embedding, 검색 방식에 따라 품질 차이가 발생한다.
- 여러 문서에 흩어진 수치·시간·규칙의 관계를 추론하는 데에는 추가 설계가 필요하다.

RAG의 핵심은 **질문이 들어온 시점에 필요한 근거를 찾아 LLM에 제공하는 것**이다.

## 3. CAG (Cache-Augmented Generation)

### 캐시 증강 생성

CAG는 검색을 매번 수행하는 대신, 제한된 규모의 지식 문서를 사전에 LLM 컨텍스트에 적재하고 Key-Value Cache(KV Cache)를 재사용하는 접근 방식이다.

쉽게 비유하면 다음과 같다.

- RAG: 질문할 때마다 도서관에서 필요한 책을 찾아온다.
- CAG: 자주 참고할 책을 미리 책상 위에 펼쳐두고 질문에 답한다.

CAG는 긴 컨텍스트를 처리할 수 있는 LLM을 활용해, 지식 전체 또는 필요한 문맥을 사전에 처리해 둔다. 이후 질의 시 미리 계산한 KV Cache를 재사용함으로써 반복적인 문맥 처리와 실시간 검색 단계를 줄인다.

### CAG 동작 구조

```text
       [사전 준비 단계]
       문서 수집 및 정제
              |
              v
      Context Window에 적재
              |
              v
        KV Cache 생성
              |
              v
       캐시 저장 및 재사용
              |
              |
       [질의 처리 단계]
              |
         사용자 질문
              |
              v
       사전 계산된 KV Cache
              |
              v
             LLM
              |
              v
          답변 생성
```

### KV Cache란?

Transformer 기반 LLM은 Attention 연산 과정에서 Key와 Value 값을 계산한다.

이전 토큰에 대해 계산한 Key와 Value를 캐시에 저장해 두면, 다음 토큰을 생성할 때 동일한 과거 문맥을 다시 계산하지 않아도 된다.

CAG는 이 KV Cache를 문서 컨텍스트에 대해 사전에 생성하고 재사용하는 방식이다.

### 언제 사용할까?

- 변경이 드문 사내 규정이나 고정된 매뉴얼
- 특정 프로젝트의 제한된 기술 문서
- 동일한 문맥을 반복적으로 참조하는 질의응답
- 문서 전체를 컨텍스트에 넣어도 모델의 입력 한도 내에 들어오는 소규모 지식베이스

### 장점과 한계

**장점**
- 질의 시점의 별도 검색 단계를 생략할 수 있다.
- 검색 과정에서 발생하는 문서 선택 오류를 줄일 수 있다.
- 반복적으로 같은 문맥을 사용하는 경우 사전 계산 결과를 재사용할 수 있다.

**한계**
- 문서가 많으면 Context Window와 KV Cache 메모리 사용량이 커진다.
- 문서가 변경되면 캐시를 다시 생성하거나 갱신해야 한다.
- 긴 컨텍스트를 처리하는 비용과 메모리 부담이 사라지는 것은 아니다.
- 모델, 토크나이저, 실행 환경에 따라 캐시 재사용 가능 조건을 고려해야 한다.

CAG의 핵심은 **질문이 들어오기 전에 필요한 문맥을 준비하고 캐시를 재사용하는 것**이다.

참고로 CAG는 모든 문서를 무조건 컨텍스트에 넣는 방식이 정답이라는 뜻은 아니다. 지식 규모가 제한적이고 반복 사용되는 상황에서 특히 검토할 만하다.

## 4. KAG (Knowledge Augmented Generation)

### 지식 증강 생성

KAG는 문서의 문장 유사도만으로 답을 찾기 어려운 문제를 해결하기 위해 지식 그래프(Knowledge Graph), 벡터 검색, 논리적 추론 등을 결합하는 접근 방식이다.

RAG가 질문과 유사한 문서를 찾는 데 초점을 둔다면, KAG는 데이터에 포함된 개체와 개체 사이의 관계, 규칙, 수치, 시간 정보를 함께 활용하는 데 초점을 둔다.

예를 들어 다음과 같은 정보가 있다고 가정하자.

- A 직원은 2024년 1월 1일 입사했다.
- B 직원은 2025년 3월 1일 입사했다.
- 회사의 승진 규정은 근속 2년 이상이다.

질문은 다음과 같다.

> A 직원과 B 직원 중 누가 승진 요건을 먼저 충족하나요?

단순히 관련 문장을 검색하는 것만으로는 부족하다. 직원, 입사일, 근속 기간, 승진 규정 사이의 관계를 연결하고 날짜를 비교해야 한다.

### Knowledge Graph란?

Knowledge Graph는 정보를 개체(Entity)와 관계(Relationship)로 표현한 그래프 구조다.

예를 들어 다음과 같이 표현할 수 있다.

```text
[직원 A]
   |
   | 입사일
   v
[2024-01-01]

[직원 B]
   |
   | 입사일
   v
[2025-03-01]

[승진 규정]
   |
   | 요구 근속 기간
   v
[2년 이상]
```

실제 지식 그래프에서는 개체와 관계를 노드(Node)와 엣지(Edge)로 표현하고, 이를 통해 여러 단계의 관계를 탐색할 수 있다.

### KAG 동작 구조

```text
       기업 문서 / 업무 데이터
                |
                v
       Entity 및 관계 추출
                |
                v
        Knowledge Graph
                |
                v
       질문 분석 및 질의 계획
                |
                v
       그래프 + 문서 Hybrid 검색
                |
                v
       논리적 추론 및 계산
                |
                v
               LLM
                |
                v
             답변 생성
```

여기서 중요한 점은 KAG가 Knowledge Graph만 사용하는 단순한 구조가 아니라는 것이다. 대표적인 KAG 프레임워크는 지식 그래프와 원본 문서 Chunk를 연결하고, 벡터 검색 및 논리적 추론을 함께 활용한다.

### 언제 사용할까?

- 인사정보와 조직 간 관계 분석
- 금융 데이터의 수치 및 시간 조건 분석
- 기업 업무 규칙과 프로세스 분석
- 여러 문서에 흩어진 정보 간 관계 추론
- 다단계 질문(Multi-hop Question Answering)

### 장점과 한계

**장점**
- 문서와 데이터 사이의 관계를 명시적으로 표현할 수 있다.
- 여러 단계의 관계를 따라가는 질문에 유리하다.
- 수치, 시간, 업무 규칙 등의 논리적 조건을 활용할 수 있다.

**한계**
- Knowledge Graph를 구축하고 유지해야 한다.
- 개체 추출과 동일 개체 연결(Entity Linking)의 품질이 중요하다.
- 데이터 모델과 관계 스키마를 설계해야 하므로 구현 난도가 높다.

KAG의 핵심은 **정보 자체뿐 아니라 정보 사이의 관계와 규칙을 활용해 답을 도출하는 것**이다.

## 5. RAG vs CAG vs KAG 비교

| 비교 항목 | RAG | CAG | KAG |
|---|---|---|---|
| 핵심 접근 | 검색 | 사전 캐싱 | 지식 관계 및 추론 |
| 정보 활용 | 질문마다 관련 정보 검색 | 문맥을 미리 적재 | 그래프·문서·규칙 활용 |
| 주요 구성 | Retriever, Vector DB, LLM | Context, KV Cache, LLM | Knowledge Graph, Hybrid Retrieval, Reasoning |
| 지식 업데이트 | 검색 인덱스 갱신 | 캐시 재생성 | 그래프 및 원본 지식 갱신 |
| 강점 | 다양한 문서에서 필요한 근거 검색 | 반복 문맥 처리 최적화 | 복잡한 관계 및 다단계 추론 |
| 주요 부담 | 검색 품질 관리 | Context 및 캐시 메모리 | 그래프 구축 및 관리 |
| 적합한 환경 | 변경되는 문서가 많은 환경 | 규모가 제한되고 고정된 지식 | 관계와 규칙이 중요한 전문 영역 |

세 기술은 다음 질문으로 구분하면 이해하기 쉽다.

- RAG: 필요한 정보를 어디서 찾아올까?
- CAG: 필요한 정보를 미리 준비해 재사용할 수 있을까?
- KAG: 정보 사이의 관계를 어떻게 이해하고 추론할까?

## 6. 실제 기업용 AI 시스템에서는 어떻게 선택할까?

기술을 선택할 때는 유행보다 데이터의 특성과 질문의 유형을 먼저 살펴봐야 한다.

### 상황별 선택

| 업무 상황 | 추천 접근 | 이유 |
|---|---|---|
| 사내 취업규칙 검색 | RAG | 문서 검색과 근거 제시가 중요 |
| 자주 변경되는 업무 매뉴얼 | RAG | 문서 갱신 및 검색이 필요 |
| 고정된 제품 매뉴얼 Q&A | CAG 검토 | 제한된 문맥을 반복 활용 |
| 직원별 근속 및 승진 요건 분석 | KAG 검토 | 개체 관계와 날짜 조건 추론 |
| 부서·조직·업무 권한 분석 | KAG 검토 | 여러 개체 간 관계 연결 |

### 서로 조합할 수도 있을까?

가능하다. 실제 시스템에서는 각각의 장점을 결합할 수 있다.

**RAG + KAG**

- 벡터 검색으로 관련 문서 Chunk를 찾는다.
- Knowledge Graph로 관련 개체와 관계를 탐색한다.
- 두 검색 결과를 결합해 답변을 생성한다.

**RAG + CAG**

- 공통으로 사용하는 시스템 규칙이나 고정 문맥은 캐싱한다.
- 변경되는 업무 문서는 RAG로 검색한다.
- 검색 결과와 캐시된 문맥을 함께 LLM에 전달한다.

**KAG + LangGraph**

- 질문 유형에 따라 검색 또는 그래프 추론 경로를 선택한다.
- 필요한 경우 여러 단계의 검색과 검증을 수행한다.
- 최종 결과를 구조화해 반환한다.

다만 조합이 많아질수록 데이터 동기화, 캐시 무효화, 검색 결과 통합 등의 설계가 복잡해진다는 점도 고려해야 한다.

## 7. 실제 프로젝트에 적용한다면?

HR 문서와 재무 문서를 활용하는 기업용 AI를 개발한다고 가정해 보자.

처음부터 모든 기술을 도입하기보다는 단계별로 확장하는 것이 좋다.

### Step 1. RAG 구축

- PDF, DOCX 문서 파싱
- 문서 구조를 고려한 Chunking
- Embedding 및 Vector DB 저장
- 검색 결과와 근거를 활용한 답변 생성

### Step 2. Advanced RAG

- BM25 + Vector Search Hybrid Retrieval
- Reranker 적용
- 검색 결과 평가
- 검색 실패 시 Query Rewrite 및 재검색

### Step 3. LangGraph 적용

- 질문 유형 분류
- HR / Finance 검색 경로 분리
- 검색 결과 검증
- 실패한 단계만 재시도

### Step 4. KAG 확장

- 직원, 부서, 규정, 계정과목 등의 Entity 추출
- 개체 간 관계 정의
- Knowledge Graph 구축
- 여러 문서에 걸친 관계 추론

### Step 5. CAG 검토

- 공통으로 참조하는 고정 문맥 선정
- 사전 KV Cache 생성
- 반복 질의에서 성능 측정
- RAG 방식과 비용 및 응답 속도 비교

이 순서가 반드시 정답은 아니지만, 문서 기반 AI를 처음 구축하는 프로젝트에서는 RAG를 먼저 구현하고 실제 한계를 확인한 뒤 확장하는 접근이 현실적이다.

---

## 8. 마무리

RAG, CAG, KAG는 모두 LLM이 외부 지식을 활용하도록 돕는 기술이지만, 각각 해결하려는 문제가 다르다.

- **RAG:** 필요한 정보를 검색해서 답변한다.
- **CAG:** 필요한 문맥을 미리 적재하고 캐시를 재사용한다.
- **KAG:** 지식 간 관계와 논리를 활용해 추론한다.

중요한 것은 어떤 기술이 가장 뛰어난가가 아니다.

내가 구축하려는 AI 시스템에서 데이터가 얼마나 자주 변경되는지, 문서 규모는 어느 정도인지, 단순 검색으로 충분한지, 여러 정보 간 관계를 추론해야 하는지를 먼저 판단해야 한다.

개인적으로 기업용 문서 AI를 처음 개발한다면 RAG를 기반으로 시작하고, 관계 추론이 필요한 영역에 KAG를 적용하며, 고정된 문맥의 반복 처리 비용이 큰 경우 CAG를 검토하는 순서를 추천한다.
